# P&ID (PDF) → DEXPI + databases

Lokale React-app met een Node/TypeScript-pipeline die een P&ID-tekening in PDF leest met Claude (vision) en per project een DEXPI 2.0.1-model, CSV-tabellen en een SQLite-database maakt. De opzet volgt de Corvic-playbook *P&ID Read* (`inspiration_corvic_ai/`), aangevuld met leidingtracering en DEXPI-export in hetzelfde formaat als `DrawBite_PDF2DEXPI_v1`.

## Starten

```bash
npm install
export ANTHROPIC_API_KEY=sk-ant-...   # of `ant auth login`
npm run dev
```

Open <http://localhost:5173>. Kies links een PDF uit `input/` (of sleep een nieuwe erin), kies de instellingen en klik **Start pipeline**. De voortgang loopt live mee in de stappenbalk.

Zonder UI (bijvoorbeeld voor een batch):

```bash
npm run pipeline -- input/R9-001.pdf --depth verified --effort medium
```

Productie-build: `npm run build && npm start` → <http://localhost:5175>.

## Pipeline

| stap | wat | uitvoer |
|---|---|---|
| locate | PDF profileren (pdfinfo), rasteren met pdftoppm tot ±5600 px lange zijde, titelblok + symboolnorm lezen | `pages/`, `drawing.profile.json` |
| digitize | blad in overlappende tegels (1400 px, 20 %), elke tegel lezen met structured output, terugprojecteren en ontdubbelen op tag/nabijheid; daarnaast één blik op het hele blad voor grote apparatuur (vaten, tanks, fermentors) die groter is dan een tegel — dat kader vervangt de afgesneden tegelstukken | `tiles/`, `work/major_p*.json`, `drawing.xml` |
| verify | audit per blok tegen de tekening; fixes ≥ 0,85 automatisch, 0,60–0,84 met commentaar, < 0,60 naar open punten. `fast` = geen audit, `exhaustive` = tot 4 rondes zolang de score > 0,02 stijgt | `drawing.verified.xml`, score |
| vector (in digitize/connect) | uit een CAD-PDF de exacte lijnen en (waar aanwezig) de echte tekst halen (`pdftocairo -svg`, `pdftotext -bbox`); lijnen samenvoegen tot *netten*, geknipt bij elk symbool, met herkende stippellijnen en overbrugde onderbrekingen (kruisingen, lijnlabels, stroompijlen). Echte PDF-woorden vervangen OCR. Bij een scan doet deze laag niets | `work/nets_p*.json`, `work/nets_p*.png` |
| connect | leidingen volgen (van/naar, componenten in stroomvolgorde, aftakkingen) en instrumentkoppelingen | `drawing.model.json` |
| tabulate | tabellen equipment, instruments, valves, piping_components, off_page_connectors, lines, line_components, signals (met `basis` en `via`), signal_lines, unresolved | `tables/*.csv`, `database/pid.sqlite`, `output/_catalog.sqlite` |
| dexpi | DEXPI 2.0.1 (Core/Plant + Core/Diagram-tekeninglaag): apparatuur met nozzles, PipingNetworkSystems/Segments/Pipes met PipeTees, off-page connectors, instrumentfuncties, lussen, actuating systems; zelfcontrole op ids en referenties | `<project>.dexpi.xml`, `<project>.dexpi.svg`, `dexpi_report.json` |
| report | antwoord in de vaste vorm van de playbook + leesbaar rapport | `drawing.answer.json`, `report.md` |

`output/_catalog.sqlite` bevat dezelfde tabellen voor alle projecten, met een kolom `project`.

## Runs en opnieuw lezen

Het model leest dezelfde tekening niet twee keer precies hetzelfde. Daarom wordt elke run van een project volledig bewaard, en kun je een tekening opnieuw laten lezen en daarna kiezen welke lezing geldt.

- **Alles bewaard.** Elke run staat in `output/<project>/runs/run-<n>/`: model, DEXPI (+ SVG), tabellen, beide databases, overlay, open punten, rapport, log, paginabeelden en werkbestanden. De tegels die naar het model gingen (`tiles/`) worden niet bewaard. Een project van vóór deze opzet krijgt bij zijn volgende run automatisch `run-1`.
- **Actieve run.** `output/<project>/` zelf is altijd de actieve run, dus alle scripts (`redexpi`, `overlay`, `score`, `vectorcheck`) werken daar op. Bij wisselen wordt de actieve run eerst teruggeschreven naar zijn eigen map, zodat een herberekening sindsdien niet verloren gaat. De catalogus `_catalog.sqlite` volgt de actieve run.
- **Tab *Runs*.** Alle runs naast elkaar: op de PDF, leiding en signaal gevolgd, open punten, aantallen, kosten. De run met de beste overlay (gemiddelde van *op de PDF* en *leiding gevolgd*) krijgt het label *beste*. Met **Maak actief** kies je welke run de andere tabbladen tonen.
- **Correctie (aanbevolen).** Een volledige herlezing bleek op PID024 en PID034 slechter dan run 1. Dat komt door spreiding tussen lezingen: wat run 1 goed had, kan bij een nieuwe lezing misgaan. Een correctie laat de lezing van de actieve run daarom staan en kijkt alleen opnieuw naar de verdachte plekken:
  - open punten;
  - getekende lijnen die de run niet gebruikt en getekende stukken die niet op de PDF staan (≥150 px, elk max. 15);
  - tags die je in je opmerkingen noemt.

  Plekken die dicht bij elkaar liggen worden samengevoegd tot max. 10 ingezoomde uitsneden. Per uitsnede doet het model één call met het hele blad als overzicht. Het antwoordt per punt met *opgelost*, *klopte al* of *nog open*, en geeft daarbij itemcorrecties (toegepast vanaf zekerheid 0,6) en leidingcorrecties (vanaf 0,7). Daarna draait de vectorlaag opnieuw, en komen tabellen, DEXPI, rapport en overlay opnieuw uit die vectorlaag. Werkbestanden staan in `work/correct_<n>.json`.

  **Per wijziging beoordeeld.** De wijzigingen worden één voor één op een kopie toegepast: elke itemcorrectie apart, elke leidingcorrectie apart, nieuwe leidingen samen. Na elke wijziging volgen vectorlaag, DEXPI-tekening en overlay, in het geheugen en zonder model-calls (ca. 0,1 s per wijziging). Een wijziging blijft alleen staan als de overlay daardoor niet zakt; één afrondingsstap van 0,05 %-punt mag. Zo kost één verkeerde leidingwijziging niet meer de goede itemcorrecties eromheen. Een punt telt als *opgelost* alleen als geen afgewezen of te onzekere wijziging over zijn items gaat; anders blijft het open met wat de tweede blik zag. Een punt dat al klopte telt altijd. In het log staat welke wijzigingen zijn afgewezen en met hoeveel ze de overlay verlaagden.

  **Bewaking van de hele run:** de correctie wordt alleen actief als de overlay minstens even goed is (gemiddelde van *op de PDF* en *leiding gevolgd*, marge 0,2 %-punt) en er niet meer open punten zijn. Anders wordt de vorige run weer actief en staat de correctie als aparte run ernaast. Het oordeel staat in `run.json` (`rerun.verdict`) en in de tab *Runs*. Je kunt een correctie ook op een correctie draaien; die bekijkt dan de punten die nog open zijn.
- **Correctie, proeven** (*op de PDF* / *leiding gevolgd*, open punten):

  | Project | Uitgangsrun | Na correctie | Kosten |
  |---|---|---|---|
  | PID034 | run 1: 96,3 / 82,2, 22 open | run 4: 96,3 / 82,2, 10 open | $0,52 |
  | R4_026 | run 2: 97,1 / 71,0, 7 open | run 4: 97,6 / 75,8, 4 open | $0,23 |
  | PID024 | run 1: 86,8 / 74,0, 21 open | run 5 → run 6: 88,0 / 74,3, 12 open | $0,83 + $0,69 |

  - **PID034:** V186 kogelkraan → schuifafsluiter, drie dubbele aansluitboxen weg, bestemmingstekst als omschrijving.
  - **R4_026:** de bewaking wees de FIL-3-tag af (−3,8 pt): die maakte van twee filters één. Voordat er per wijziging werd beoordeeld, keurde de bewaking de hele correctie van R4_026 af (94,8 op de PDF), en die van PID024 ook (78,8 fit).
  - **PID024:** afgewezen werden onder meer het verwijderen van een box waaraan een getekende leiding hing en het omleggen van L1-006 (−1,9 pt).
- **Volledig opnieuw lezen.** Een volledige nieuwe lezing (kosten als de eerste) die meekrijgt wat de controle van de actieve run opleverde, in tags en niet in pixels:
  - jouw opmerkingen;
  - de open punten (max. 40);
  - de grootste getekende lijnen die de run niet gebruikte, en de grootste stukken waar de run iets tekent dat niet op de PDF staat (samen max. 30).

  Dat gaat als aparte sectie in de systeemprompt van alle stappen. De sectie is uitdrukkelijk geformuleerd als plekken om extra goed te kijken, niet als feiten, zodat het model niets toevoegt wat het niet ziet. Voor het starten toont de app precies wat het model krijgt. De opmerkingen en het aantal punten staan in `run.json` (`rerun`), de volledige tekst in `settings.guidance`.

## Grenzen

- Het resultaat is een digitalisering voor early engineering, geen ontwerpvrijgave. Controleer altijd tegen de bron-PDF; de tab *Tekening* legt elk gelezen item als kader over het blad.
- De DEXPI-export bevat het procesmodel én een tekeninglaag (`Core/Diagram`): elk symbool staat op zijn plek uit de PDF, leidingen zijn orthogonaal getrokken tussen de knooppunten (hoogstens één knik). Het leidingverloop volgt dus niet exact de bron. Een SVG-voorbeeld (`<project>.dexpi.svg`) staat op het DEXPI-tabblad.
- Symbolen komen uit `reference/dexpi_symbols_2.0.1.json`: de DEXPI 2.0.1-referentiesymbolen (© DEXPI e.V., CC BY 4.0) plus de FlowBite-symbolen, overgenomen uit `FlowBite_DEXPI_v1` (daar niets aangepast).
- **A/B-check na een codewijziging: `npm run ab`.** Meet alle projecten twee keer, met de code in de werkmap en met de code van een git-commit (standaard `HEAD`). Beide doen dat op dezelfde opgeslagen runs, in het geheugen, zonder iets weg te schrijven en zonder model-calls (ca. 30 s).
  - De tabel toont per project *op de PDF*, *leiding gevolgd*, *signaal*, Δfit, gerouteerde paren en `no-path`.
  - Stopt met foutcode 1 als een project meer dan de afrondingsmarge (0,05 procentpunt) achteruitgaat op fit of signaal, of niet meer draait.
  - Varianten: `npm run ab -- main~3` (tegen een oudere commit) en `npm run ab -- HEAD R9 PID024` (alleen die projecten).
  - Zo blijft "de code mag niet slechter worden" een vaste controle. Gebruik: wijzigen → `npm run ab` → pas committen als er geen ✗ staat → daarna `npm run redexpi` op de projecten die ✓ beter laten zien.
- **Verliesanalyse: `npm run loss`.** Laat zien waar de overlay-punten verloren gaan (alle projecten, in het geheugen, ca. 30 s; `npm run loss -- R9 -v` toont per oorzaak de grootste gevallen met plek en items).
  - Elk getekend net wordt opgeknipt in stukken tussen de symbolen die het verbindt (kortste weg langs het net; een stuk in een lus, zoals een bypass, hoort bij het dichtstbijzijnde symbool aan elke kant). Elk gemist stuk krijgt een oorzaak:
    - *geen item*: het net raakt zelf geen symbool;
    - *open: niets gelezen*: het stuk loopt naar een los uiteinde zonder gelezen symbool (pijl, tekst, ongelezen symbool);
    - *open: symbool vlakbij*: dat losse uiteinde ligt vlak bij een symbool dat het net niet raakt;
    - *open einde*: overig, niet tussen twee symbolen;
    - *niet in model*: het stuk ligt tussen symbolen die het model niet met een leiding verbindt;
    - *route mislukt* (met de reden van de router);
    - *geen route*: het model verbindt ze, maar er is geen route gevraagd;
    - *andere weg*: er is wel een route getekend, maar elders.
  - Signaallijnen idem, met de signaalkoppelingen van het model.
  - `npm run loss -- --pairs`: de paren achter *niet in model*, per soort (bv. apparaat–afsluiter) en de grootste afzonderlijk.
  - Eerste resultaat (*niet in model* 5,6 → 4,5 %): twee fouten in het toevoegen van getekende leidingen die de runs missen.
    - Een net met een symbool in honderden mini-stukjes (een slang als golflijn) viel uiteen in delen zonder los uiteinde, waardoor `netPath` geen weg vond. Zulke delen worden nu via hun dichtstbijzijnde knopen gekoppeld.
    - Een terugslagklep met "junction" in de omschrijving gold als elektrisch kastje; alleen "junction box" telt nog.
    - R3_026 *leiding gevolgd* 92,6 → 97,0 %; R9 69,0 → 72,3 % (*op de PDF* 72,6 → 73,1 %); PID023 +0,2. Geen project slechter.
  - Tweede ronde ("inline instrumenten"): de grootste paren bleken geen instrumenten op de leiding. Het waren kleppen waarvan OCR het kader op de tag-tekst had gezet; het klepsymbool zelf telde daardoor als gemiste leiding.
    - `fitSymbols` (vectorlaag, naast `fitBubbles` en `fitEquipment`) zet zo'n kader op het getekende symbool ernaast: een klein cluster korte strepen met een schuine streep, waar een leiding doorheen loopt. De twee helften van een kogelkraan (met de kogel ertussen) zijn één symbool.
    - Voorzichtig: een kader dat al op een symbool aan de leiding ligt blijft staan, een symbool in het kader van een ander item is van dat item, en een tag die ongeveer even dicht bij twee symbolen staat blijft onaangeroerd.
    - PID016 *leiding gevolgd* 73,7 → 76,4 %; R10 73,2 → 74,7 % (*op de PDF* 87,4 → 87,5 %). Geen project slechter.
  - Lijnsprongen (`hops.ts`): waar een leiding met een boogje over een andere springt, bleven de boogstukjes in de vectorlaag staan. Als korte rechte stukjes getekend lag de top van de boog op de gekruiste leiding en gold als T-stuk, waardoor op één tekening bijna alle leidingen één net werden (41 000 px, 23 items).
    - Nieuw herkend: een boog als polylijn, een rij sprongen over een paar lijnen naast elkaar, en een gekruiste lijn die een px of twee scheef loopt. De stukjes van zo'n boog gaan eruit; een recht stuk overbrugt het gat.
    - PID034 *leiding gevolgd* 82,3 → 88,0 %; *op de PDF* 96,3 → 94,0 %: één route volgde eerst de valse verbinding (op de PDF, maar fout) en wordt nu een knik, omdat de echte aansluiting op een leiding van een andere lijndikte ligt. Andere projecten ongewijzigd.
    - Redexpi is weer idempotent: `joinDrawnPipes` voegde bij elke run dezelfde leidingen opnieuw toe. Hij voegt nu geen leiding toe die al precies zo bestaat, en `dropDuplicateRuns` ruimt eerder dubbel toegevoegde op (alleen door `joinDrawnPipes` toegevoegde leidingen, nooit getraceerde). De A/B tegen een oudere versie toont daardoor bij R9 −0,3 *op de PDF*: de oude code legt 9 dubbele leidingen bovenop bestaande routes.
    - Geprobeerd en verworpen: elk piepklein stukje dat midden op een lijn eindigt negeren (R9 −1,8, HMD signaal 62 → 51 %); en de aftakplek uit de nets halen (`after` meestal al goed; de wijzigingen waren deels aantoonbaar fout).
  - Verder: verzonnen lijnstukken per soort lijn, en de uitkomst van alle routes die de tekening vraagt.
- **Openbare kopie.** Bij elke push naar `main` maakt de GitHub Action `.github/workflows/public-mirror.yml` een schone kopie en zet die in de openbare repo `pdf2DEXPi_v2-public`.
  - Wat eruit blijft: klanttekeningen (`input/`), antwoordsleutels (`reference/keys/`), `inspiration_corvic_ai/` en het gebouwde OCR-programma.
  - Klant- en projectnamen worden vervangen door hun code (bijv. `R9-001`).
  - De Action stopt als er nog een klantnaam in de kopie staat.
  - De openbare repo krijgt alleen momentopnames, nooit de geschiedenis van deze repo.
  - De regels staan in `scripts/public-export.json`; dat bestand wordt zelf niet gepubliceerd. Een nieuwe klant voeg je daar toe aan `forbidden`.
  - Lokaal bekijken wat er gepubliceerd zou worden: `node scripts/public-export.mjs /tmp/public` (werkt op de laatste commit).
  - Eenmalig nodig: een token met schrijfrecht op alleen de openbare repo, als secret `PUBLIC_REPO_TOKEN` van deze repo.
- Alles na het gelezen model opnieuw maken — tabellen, databases, DEXPI en rapport, plus de reparaties uit de getekende lijnen (open eindes sluiten, losse afsluiters plaatsen, ontbrekende getekende leidingen toevoegen, instrumenten koppelen; net als de connect-stap en de A/B-check) — zonder model-calls (bv. na een wijziging in de writer of een handmatige correctie in `drawing.model.json`): `npm run redexpi` (alle projecten) of `npm run redexpi -- <project>`. Past ook de huidige tag- en OCR-regels toe.
- **Antwoordsleutels en score.** Per tekening staat de handgecontroleerde waarheid in `reference/keys/<project>.key.json` (een nieuwe run overschrijft die niet). Maak een concept uit de huidige uitlezing en controleer het in de app, tab **Sleutel**: K = klopt, X = staat niet op de tekening, velden aanpassen = gecorrigeerd, **+ Ontbrekend item** = kader slepen, koppelingen per instrument afvinken of toevoegen. Score van de huidige uitlezing: knop in de tab, of `npm run score` (alle projecten met een sleutel; `-v` toont gemist / te veel / anders gelezen). Concept vanaf de commandoregel: `npm run score -- --draft <project>`.
- **Leidingen langs hun getekende route, T-stukken op hun echte plek.** Op vectorbladen bouwt de DEXPI-stap per blad een routeplanner over alle getekende leidingstukken. Die verbindt stukken die op elkaar eindigen of in een T op elkaar uitkomen, en overbrugt een korte onderbreking (pijlpunt, stromingspijl) als het stuk in dezelfde richting doorloopt en er geen symbool tussen zit.
  - Een leiding waarvan de uiteinden niet door één getekend lijnstuk verbonden zijn (via een T-stuk, een andere lijn of een nozzle) volgt nu die getekende route.
  - Een T-stuk komt waar de getekende aftakking werkelijk op de hoofdleiding uitkomt.
  - Geen route, of alleen een omweg langer dan 1,4× de afstand: dan zijn de twee uiteinden op de tekening niet verbonden. De oude lijn met één knik blijft staan en is in de overlay rood te zien.
  - Stukken van één getekende lijn die net niet op elkaar aansluiten (kleine verspringing in de CAD-tekening) verbindt de planner alsnog, zodat zo'n leiding niet terugvalt op een verzonnen knik.
  - Een symbool waar de getekende lijn dwars doorheen loopt (afsluiter in de leiding, bel op de lijn) is ook een startpunt; een T-stuk dat net naast de lijn geschat is, mag tot 3× zo ver naar de lijn zoeken. Het DEXPI-rapport meldt per tekening hoeveel leidingen de getekende route volgen en waarom de rest dat niet doet (`shared`, `no-path`, `no-start-…`).
  - T-stukken zonder getekende hoofdleiding tussen de twee buren: de router volgt de aftakking naar elk van beide buren, en het T-stuk komt waar die twee getekende routes uit elkaar gaan. Ligt het T-stuk aan het eind van een run (één buur), dan komt het op de getekende route tussen die buur en de aftakking.
  - **Overspringende leidingen.** Een leiding die met een halve cirkel over een andere lijn springt, is in de PDF onderbroken. De boog zelf telt niet als leidingstuk, dus de leiding viel daar uiteen, en een stuk tussen twee sprongen werd als losse streep weggegooid. `pipeline/hops.ts` herkent de sprong en legt een recht stuk over het gat (in `Seg` gemarkeerd als `hop`). Dat gebeurt direct bij het inlezen van de vectoren, zodat netten, router, DEXPI-tekening en overlay er allemaal mee werken. Twee tekenstijlen worden herkend, steeds tussen twee leidingeinden die exact op één lijn tegenover elkaar liggen:
    - één pad van stompje – Bézier-boog – stompje;
    - een vlak van minidriehoekjes aan één kant van het gat, dat het gat overspant en aan beide leidingeinden vastzit, met de gekruiste lijn die aan de boogkant duidelijk doorloopt. Een symbool dat aan beide kanten om de lijn ligt (koepel, bel), telt niet.

    Gevonden en visueel gecontroleerd: PID024 6, PID034 11, R3_026 1, de andere tekeningen 0. Op de overlay (*op de PDF* / *leiding gevolgd*) gaf dat:
    - PID024: 88,2 / 74,3 → 93,5 / 83,8;
    - PID034 en R3_026: elk +0,1 op *leiding gevolgd*;
    - de andere elf projecten: ongewijzigd.
  - **Leidingen die langs een symbool lopen.** Bij een symbool op een leiding, zoals een condenspot of een in-line instrument, is het korte streepje naar de leiding soms symboolgeometrie. Een route vond dan geen weg (`no-path`). Een getekende lijn die door het symboolkader loopt of er vlak langs gaat (binnen max(3 px, 0,0015·W)), mag de route nu ook laten beginnen of eindigen, op het punt waar die lijn het symbool passeert.
    - Dit geldt alleen voor in-line symbolen. Apparaten (tanks e.d.) doen niet mee, anders kaapt een leiding die door een tank loopt de route.
    - Het is een terugvaloptie. Eerst wordt gerouteerd over de eigen getekende einden van het symbool, en alleen als dat niet lukt, komen de passerende lijnen erbij. Bestaande routes blijven dus gelijk.
    - Resultaat (A/B in het geheugen, alle 14 projecten): R9 *op de PDF* 70,0 → 72,6 % en *leiding gevolgd* 66,3 → 69,0 %. HMD en PID024 gaan +0,1 omhoog. Geen enkel project gaat achteruit.
    - Een eerste versie zonder terugvalvolgorde kostte R10 0,1, omdat een hoofdleiding die precies langs de bovenrand van een afsluiterkader liep, de route overnam.
    - De resterende `no-path`-gevallen in R9 zijn vooral leesfouten: het kader van een afsluiter is de tagballon erboven, of een paar wijst naar een tag op een ander blad.
  - **Haakse bochten** zijn gemeten en in orde. Van de ca. 2.400 hoeken waar een horizontaal en een verticaal leidingstuk samenkomen, belanden alle echte leidinghoeken in één net. De 14 "gesplitste" hoeken bleken flensparen, pijlpunten of een logo. Afgeronde bochten komen in deze tekeningen niet voor.
  - Een apparaatkader met een afsluiter en nog minstens één ander onderdeel erin (vat met inwendig leidingwerk, skid) is een container: de leidingen die erin getekend zijn tellen als proces, niet als symbooltekening.
- **Titelblok herkend uit de tekening.** Het model levert geen kader van het titelblok, dus de vectorlaag zoekt het zelf: een deel van het tekeningkader zonder symbolen, afgesneden door een lijn van kaderzijde tot kaderzijde (strook onderaan of kolom rechts), of een blok in de hoek rechtsonder. Lijnen die als dunne gevulde rechthoek getekend zijn tellen mee. Gecontroleerd op alle 14 vectorbladen: 11 keer gevonden (soms alleen het logo-/hoekblok), nergens op procesonderdelen; 3 keer niets (dan verandert er niets). De lijnen daarin tellen niet meer als leiding of signaal.
- **Leidingdikte alleen uit lijnen die een symbool raken.** De dikte die als 'leiding' geldt (waaronder een lijn een dunne impulslijn is) werd over alle lijnen bepaald, ook kader, titelblok en legenda. Nu alleen over lijnen die een symbool raken. Bij R10 worden zo de impulslijnen van TI/TT/PI naar de leiding herkend (2 → 16 signaallijnen); bij R5_015 telt de leiding onder rotameter FI 132 terecht niet meer als signaal.
- **Geen schijn-signaallijnen.** Niet als signaallijn: de eigen omlijning van een instrumentsymbool (het vierkant van een shared-display-symbool, dat de bel aan drie of meer kanten omsluit), en een los streepje bij één bel (korter dan 0,6% van de bladbreedte). Dat haalt bij R8_013/R8_014 ruim 50 lege rijen uit de tabel `signal_lines`; de overlay-score daar zakt 0,2–0,3 punt omdat die streepjes wel op de tekening lagen.
- **Geen leiding tussen twee kaders die elkaar raken.** Het aanvullen van getekende leidingen die het model miste, maakt geen leiding meer tussen twee symbolen waarvan de kaders tegen elkaar liggen: die lijn is hun gedeelde rand (twee tagkaders naast elkaar), geen leiding. Bij R4_026 gaf dat een onterechte leiding L1-015 tussen M-201 en M-202.
- **Leiding deels langs de tekening.** Vond de router geen getekend pad tussen de twee uiteinden van een leiding (meestal een T-stuk dat een eind naast de getekende lijn ligt, of een lijn die half dik en half dun getekend is), dan werd de hele leiding een rechte knik over leeg papier. Nu volgt hij de getekende lijn vanaf één uiteinde zo ver als die richting het andere uiteinde gaat, en tekent alleen het restje als knik. Alleen als dat restje kort is (hoogstens een kwart van de afstand en 3% van de bladbreedte) en het pad geen omweg is. `dexpi_report.json` telt deze leidingen apart ("N of them partly"). Effect op precisie / leiding gevolgd: R10 64,6/60,6 → 86,5/73,0, R8_014 77,0/45,2 → 81,2/58,5, PID016 87,2/65,5 → 90,8/73,7, PID024 80,9 → 86,5 precisie; geen tekening slechter.
- **Afgeleide signaalkoppelingen niet tekenen.** Een koppeling die de app zelf afleidt uit het lusnummer (basis "loop") staat niet als lijn op de PDF. Die blijft in DEXPI en de tabellen, maar krijgt geen lijn meer (eerder een knik dwars over het blad). R8_013 precisie 66,5 → 81,0, R8_014 81,2 → 88,5.
- **Signaal langs de getekende signaallijn.** Een signaal dat het model zag, maar waaraan geen getekende signaallijn gekoppeld werd (bijvoorbeeld een databus "–o–o–" die net onder het tagvak begint), loopt nu langs de dunne en gestreepte lijnen van de PDF, nooit over een leiding; alleen het restje is een knik. R5_015 precisie 77,7 → 90,2 en signaal gevolgd 59,3 → 63,6; R10 en R8_014 iets beter. `dexpi_report.json` telt deze signalen ("signals along thin drawn lines").
- **Naamlabel met aanwijslijn is geen afsluiter.** Staat de tag van een afsluiter in een kader met een aanwijslijn (een ovaal "1CTV6" met een pijl naar het symbool), dan leest het model soms het kader als de afsluiter en mist het echte symbool. Op vectorbladen herkent de verbindingsstap zo'n kader (breed, met een rechte boven- en onderrand), volgt de enige aanwijslijn tot de pijlpunt en zet de afsluiter daar: op het symbool dat daar zonder tag gelezen is (dat gaat erin op), of anders op de leiding bij de pijlpunt, midden in de onderbreking waar het symbool de leiding doorsnijdt. Op PID024 verplaatst dit 8 afsluiters naar hun symbool; op de andere 13 vectorbladen vindt het niets. Het labelkader blijft bewaard als `label_box` op het item; de overlay telt dat kader en de aanwijslijn niet als (gemiste) leiding.
- **Instrument in de leiding.** Zet de verbindingsstap een instrument (in-line flowmeter of -regelaar) tussen de onderdelen van een leiding, dan schrijft de DEXPI-stap het alleen als instrument en loopt de leiding er doorheen; een aftakking ná het instrument komt na het onderdeel ervoor. Eerder gaf dat een dubbel id en brak de run af.
- **Gemiste getekende leidingen toegevoegd.** Na het verbinden zoekt de pijplijn op vectorbladen doorgetrokken lijnen die twee leidingdelen (apparaat, afsluiter, leidingonderdeel, bladverwijzing) verbinden die in ons model nog los van elkaar staan. Zo'n lijn sluit eerst een open leidingeinde af; anders wordt het een nieuwe aftakking of een nieuwe leiding `L<blad>-<nr>` (zekerheid 0,55), met het T-stuk op de getekende plek.
  - Niet bij motoren, panelen, schakelaars of tie-ins, niet tussen twee delen van dezelfde leiding, en niet waar overlappende symboolkaders niet duidelijk zeggen welk deel de lijn raakt.
  - Effect op de leiding-dekking (overlay): HMD 59 → 63%, PID016 59 → 66%, PID023 54 → 67%, R9 60 → 65%, R10 58,5 → 60%; de precisie bleef gelijk of steeg.
- **Overlay-score: lijkt de DEXPI op de PDF?** Op vectorbladen (CAD-PDF's) leggen we onze DEXPI-tekening terug op de getekende lijnen van de PDF, zonder model-calls. Drie getallen per project:
  - *precision*: welk deel van onze lijnen (leidingen, meet- en signaallijnen) op een getekende lijn ligt. De rest is verzonnen, bijvoorbeeld een knik waar de leiding recht loopt, of een leiding over leeg papier.
  - *pipe recall*: welk deel van de getekende doorgetrokken proceslijnen wij ook tekenen. Daaronder vallen ook doorgetrokken instrumentaansluitingen. Een lijn telt mee als hij een symbool raakt, er net voor stopt (pijlpunt) of via andere lijnen bij een symbool uitkomt. Kader, zonegrenzen en de omtrek van apparaten tellen niet.
  - *signal recall*: hetzelfde voor gestreepte lijnen.

  In de app: tabblad **Overlay** per project (scores, het plaatje, de grootste gemiste en verzonnen stukken) en het kaartje *Op de PDF* bovenaan.
  Elke run en `redexpi` schrijven `overlay.json` en `overlay-p<n>.png`: het blad vervaagd, groen = onze lijn op de tekening, rood = verzonnen, blauw = getekend maar gemist. Alle projecten: `npm run overlay` (`-v` geeft de grootste gemiste en verzonnen stukken met hun plek). `npm run compare` toont de drie getallen voor oud en nieuw. Een scan heeft geen vectorlaag en dus geen overlay-score.
- **Legenda per tekening voor de overlay (`reference/overlay-legend.json`).** Sommige tekeningen tekenen niet-leidingen even doorgetrokken als leidingen, bijvoorbeeld een opvangbak onder een tank, motorbekabeling of weegcelkabels. Die telden als "gemiste leiding" en drukten *leiding gevolgd* onterecht.
  - Per tekening staan in het bestand de lijndiktes die geen procesleiding zijn, met wat het is. De overlay telt netten van die dikte niet als getekende leiding (`ignored` in het resultaat).
  - Een dikte wordt alleen toegevoegd na controle op de tekening dat geen enkele leiding die dikte heeft. Een algemene regel (op dikte, of "lijn naar een instrumentbubbel") is gemeten en verworpen, omdat die ook echte leidingen wegstreepte (bijv. de procesleiding met TT67 in PID016).
  - Nu ingevuld voor de twee R8-tekeningen (zelfde tekenstijl): R8_013 *leiding gevolgd* 50,9 → 66,3 % en R8_014 58,5 → 78,1 %. Dat is een correctie van de meetlat, geen betere uitlezing. *Op de PDF* blijft gelijk en de andere projecten veranderen niet.
  - Het bestand noemt klantnamen en gaat dus niet mee naar de openbare kopie.
- **Vaste tellingen per tekening.** Lichter dan elk item nakijken: zet in de sleutel een blok `counts` met wat je op de tekening hebt geteld, bijvoorbeeld `{"source": "bubbels geteld op de PDF", "date": "2026-11-23", "categories": {"instrument": 52, "valve": 59}, "instruments_by_code": {"PI": 11, "TT": 10}}`. Alle velden zijn optioneel; geef alleen wat je echt hebt geteld. Een lettercode die gelezen wordt maar niet in de telling staat, telt als afwijking. Gecontroleerd op drie plekken: aan het eind van elke run in het log (`reference counts ✓/✗`), in `npm run compare` (kolom `counted`, ✓ gelijk, ~ binnen 10 %, ✗ verder weg) en met `npm run score -- --counts [-v]`. Dat laatste stopt met foutcode 1 als een telling meer dan 10 % afwijkt, als snelle regressietest na een codewijziging. De app laat `counts` staan bij het opslaan van een sleutel.
- Onzekere auditbevindingen (< 0,6) van een bestaand project een ingezoomde tweede blik geven (één kleine call per bevinding): `npm run recheck -- [project]`, daarna `npm run redexpi`. Nieuwe runs doen dit automatisch in de verify-stap.
- **Vectorlaag.** De connect-stap krijgt de netten mee als hard bewijs (welke items één getekende lijn verbindt). Na het traceren sluit de laag open leidingeinden waar de geometrie één antwoord geeft (niet bij afvoer/ontluchting), plaatst afsluiters en componenten die op geen enkele run liggen (anders vallen ze uit DEXPI): tussen twee buren op één run, of als korte aftak (op de T van een getraceerde aftak ernaast, of op een tank) naar een open einde; alleen waar de netten één aansluitpunt geven. Verder koppelt ze instrumenten met een eigen signaallijn; bussen die veel bubbels raken tellen niet. Het log meldt hoeveel buurparen in de runs door een getekende lijn bevestigd worden (`vector check`). Zonder model-calls op bestaande projecten: `npm run vectorcheck -- [project]` (rapport, `-v` toont de niet-bevestigde paren; `--apply` schrijft de reparaties weg, daarna `npm run redexpi`).
- **Signaallijnen als eigen objecten.** Elke gestippelde lijn, en elke dunne doorgetrokken lijn die een instrumentbubbel raakt, wordt een signaallijn met type volgens ISA 5.1: `- - -` elektrisch, `-·-·` software/datalink, `—//—` pneumatisch, `—x—` capillair, dun doorgetrokken = procesaansluiting (impulsleiding). Een lijn langs meer dan vier bubbels is een bus. Per lijn: de bubbels en andere einden (leiding, apparaat, los), lengte en route; tabel `signal_lines`. Een instrumentkoppeling waarvan beide einden op dezelfde lijn liggen krijgt die lijn als `via`. In DEXPI krijgt de Measuring/SignalLineFunction dan het `SignalConveyingType` (Electrical/Pneumatic/Capillary), en instrument→instrument-koppelingen (transmitter → regelaar) worden een eigen SignalLineFunction (`<instrument>.SS<n>`).
- **Exacte geometrie in de DEXPI-tekenlaag.** Leidingen tussen twee buren op een run volgen in het diagram de echte route uit de PDF in plaats van één knik; getekende signaallijnen staan er met hun echte vorm in (gestippeld waar ze elektrisch zijn). Bij een scan blijft de oude benadering.
- **Bubbels op hun getekende cirkel.** Een bubbel die op zijn geprinte tekst is verankerd, is maar zo breed als die tekst (bij "PI" zonder nummer een derde van de cirkel), waardoor getekende lijnen hem niet raken. Op vectorpagina's zet de connect-stap (en `redexpi`/`vectorcheck`) het vak op de getekende cirkel: boogstukken met beide uiteinden op één cirkel, rondom verspreid, middelpunt nabij de tekst, en alleen bij de gangbare bubbelmaat van dat blad.
- **Apparaten op hun getekende omtrek.** Van een groot apparaat zien de tiles soms alleen het label (een warmtewisselaar als vak van 18×35 px), waardoor leidingen ernaast eindigen. Op vectorpagina's zet de connect-stap (en `redexpi`/`vectorcheck`) het vak op de getekende omtrek: twee evenwijdige zijden van gelijke lengte, aan beide kanten gesloten door een dwarslijn (rechthoek) of door bogen (bolle bodems). Het apparaat neemt de kleinste omtrek die het vak bevat of er direct naast ligt, zonder andere apparatuur en met hooguit één afsluiter of instrument erin (anders is het een leidinglus).
- **Aansluitnamen van de tekening.** Staat er bij een apparaat een aansluitnaam gedrukt (S1…S4, T1…T4, N3), dan krijgt het leidinguiteinde die naam: in DEXPI als `SubTagName` van de nozzle, in de tabel `lines` als "VHE-58R S1". Alleen bij zekerheid: de getekende leiding loopt van de buur-component van de run naar dat punt (bij een vertakt net moet het de duidelijk kortste weg zijn), het woord is het dichtstbijzijnde aansluitwoord en dat punt de dichtstbijzijnde aansluiting bij het woord. Anders blijft het N1, N2 ….
- **Lettercode voor tagloze bellen.** Een instrument dat zonder tag is gelezen (alleen een type) krijgt de gedrukte lettercode uit de tekstlaag (PI, TT op bladen zonder lusnummers): het woord in de bel, of anders het dichtstbijzijnde binnen een belmaat, mits geen ander instrument dichterbij ligt.
- **Meetpunt op de juiste plek.** Een instrument dat een hele run meet, krijgt als `SensingLocation` het segment van die run dat het dichtst bij het aftakpunt ligt (niet meer het eerste segment). Het aftakpunt (`at` op de meetkoppeling) komt uit de vectorlaag: waar de lijn van de bubbel op de gemeten leiding uitkomt, of anders het dichtstbijzijnde punt van die leiding vanaf het losse einde van het stompje of de bubbel. De DEXPI-tekening tekent de meetlijn naar dat punt.
- **Connectors met dezelfde naam.** Een off-page-connectornaam mag vaker op een blad staan (drie connectors "VTK-16H1 TJ HTR CD TNK" voor drie condensaatleidingen). Bij het samenvoegen van tegellezingen en in verify geldt daarom: dezelfde connector alleen bij echte overlap (de helft van het kleinste vak); een plat afgekapt vak aan een tegelrand telt niet als eigen plek. Geldt voor nieuwe runs; bestaande projecten houden hun samengevoegde connectors tot een nieuwe run.
- **Loops zonder loopnummer.** Naast loops op nummer vormen instrumenten die via getekende instrument→instrument-signalen verbonden zijn een keten (bv. TT → TIC → TV, LE → LT → LIC). Bevat een keten instrumenten van precies één genummerde loop, dan sluiten de ongenummerde leden daarbij aan. Een keten zonder nummer wordt een eigen `InstrumentationLoopFunction`, genoemd naar het hoofdinstrument (regelaar, anders transmitter) en wat de keten meet, bv. `LIC/VTK-58E`. Ketens met twee loopnummers, of met twee bubbels van dezelfde lettercode die iets anders meten (twee kanalen op één aandrijving), blijven buiten beschouwing. Losse meters (PI, TI) vormen geen loop. Alleen in de DEXPI-uitvoer; `loop` in het model blijft het geprinte nummer.
- **Gedeelde off-page connectors.** Een connector heeft in DEXPI één node en kan maar één run afsluiten. Eindigen er meer runs op (condensaatleidingen naar één retourleiding, een run die een sprongetiket in- en weer uitloopt), dan houdt de run met de meeste componenten de connector en sluiten de andere met een T-stuk vlak naast de connector op die run aan. Alleen in de DEXPI-uitvoer; het tekeningmodel blijft zoals getraceerd. Het rapport meldt per connector welke runs zo zijn samengevoegd.
- **Tags zonder nummer.** Een tag van alleen letters (TT, PI, LE: tekeningen zonder lusnummers) is niet uniek op het blad. Tile-lezingen daarvan worden alleen samengevoegd als ze op dezelfde plek liggen; een box die plat tegen een tile-rand is afgekapt telt niet als positie. Op een CAD-blad met volledige tekstlaag krijgt elke gedrukte bubbel precies één item: een lezing zonder vrij gedrukt woord in de buurt is een dubbele en vervalt.
- **Oud en nieuw vergelijken** (na een pipeline-wijziging, zonder model-calls): `npm run compare -- <oude projectmap> <nieuwe projectmap>`. Aantallen per categorie, runs, open einden, koppelingen, open punten en hoeveel buurparen een getekende lijn bevestigt.
- **Tag-grammatica per tekening.** Welke gedrukte tekst als "gemiste tag" telt, volgt uit de tags die de tekening zelf heeft: dezelfde vorm (letter- en cijfergroepen, bv. `A D3` voor HV712, `A D2 A D2` voor HTJS09T01), geen langere lettergroep dan bekend, en bij een zeldzame vorm een bekende beginletter. Geen vaste stopwoordenlijst meer per project. Bij minder dan 8 tags valt het terug op het algemene patroon.
- Leidingen en instrumentkoppelingen opnieuw traceren op het huidige model: `npm run reconnect -- [project]` (één topologie-call per blad, plus ingezoomde crops voor instrumenten zonder verbinding met het proces). Alleen de instrumentkoppelingen: `npm run reconnect -- --links-only [project]`. Daarna `npm run redexpi`.
